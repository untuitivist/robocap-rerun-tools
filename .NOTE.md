# Project Notes

This file records confirmed project intent and separates it from proposals that still require
approval.

## Confirmed Intent

- The project inspects and aligns Robocap, NOKOV motion-capture, third-person video, and optional
  robowrist sensor data, then exports synchronized Rerun recordings.
- Dataset exports keep full session data by default. `package-data` may still create compressed
  sharing proxies, but ModelScope staging must never apply lossy video compression: full-session
  video is copied byte-for-byte and aligned-intersection video is cropped with lossless encoding.
- Timestamp inspection has an explicit Mocap/Robocap ratio restricted to `8` or `4`, defaulting to
  `8`. Ratio 8 means a 240 FPS Mocap baseline and `8*(n+1)` expected frames; ratio 4 means 120 FPS
  and `4*(n+1)`. Video stays at 30 FPS and third-person expected frames stay at `n+1`. The same Web
  selection is used when ModelScope staging regenerates the inspection report.
- The Web Statistics tab scans every Session under the shared collection root and groups it by the
  unique standalone `PXX` token in the Session path or direct `mocap*` directory. Session duration is
  the sum of one Robocap reference video per Segment, never the sum of camera views. Missing reports
  are generated serially by default with an explicit 8/4 ratio. Duration is partitioned into three
  mutually exclusive categories: unchecked for missing/unreadable/invalid reports, frame difference
  for counts that do not satisfy `n:ratio*(n+1):(n+1)`, and error-free for valid reports whose frame
  counts match. These categories sum exactly to total measurable duration. Timestamp diff findings,
  inferred dropped frames, missing timestamps, and frame-index issues do not alter this frame-count
  partition. The summary also maps each Session to an ordered
  anomaly list: normal, Mocap extra/missing frames, and third-person extra/missing frames. Categories
  are derived from actual versus expected frame counts per Segment and unioned per Session; missing
  or invalid reports are explicitly marked unchecked rather than normal.
- The Statistics tab uploads clean Sessions sequentially. It authenticates once, downloads the
  remote `metadata.jsonl`, and treats `(primitive_id, session_id)` as the authoritative uploaded key.
  Existing keys are skipped before missing-report generation, local frame checks, staging, or video
  processing. Each remaining Session uses an isolated
  `_modelscope_dataset/sequential/<primitive>/<session>/` root and must complete prepare, clean
  validation, and upload before the next starts. Upload gets one initial attempt plus three retries;
  after four failures the Session is skipped and the queue continues. Preparation and clean
  validation failures also skip only that Session. Completed uploads are not rolled back, and failed
  staging data is retained for retry. Every newly prepared `metadata.jsonl` row and Session manifest
  contains numeric `duration_s`, using one Robocap reference camera per included Segment; aligned
  intersections record the cropped common-timeline duration. Pending rows without a positive finite
  duration are rejected before upload. It copies full-session video byte-for-byte, uses the curated
  default Mocap selection (BVH/CSV/TRC/MP4 excluding `unnamed`), no RRD, and the
  repository saved in `.env`. Ambiguous identities and duplicate not-yet-uploaded keys are rejected.
- ModelScope staging can optionally publish only the frame-aligned intersection. Its signed Offset
  uses Robocap-frame units and the same mapping as frame-aligned RRD export. Positive Offset removes
  leading Mocap and third-person frames; negative Offset removes unmatched leading Robocap time.
  Every video and SQLite sensor is cropped to the resulting Robocap window. Staged streams have zero
  residual Offset, while manifests preserve source ranges and alignment parameters. Source Sessions
  are never modified, and full-session staging remains the default. The Web intersection ratio and
  Offset are prefilled from and kept synchronized with the RRD Export controls; users may explicitly
  override either value in the ModelScope tab after synchronization.
- Long CLI-backed Web operations must stream combined stdout/stderr into the shared Output box.
  Show elapsed time and parsed `[n/total]`/percentage progress when available, otherwise an animated
  unknown-total bar. Do not set a process timeout. Bound retained logs to 1000 lines or about 256 KiB.
- Every Rerun export uses one sensor layout: `middle_mag` spans the two Robocap IMU rows beside
  left/right ACC and GYRO pairs, followed by one three-column MAG/ACC/GYRO row for each available
  left/right wrist. Missing streams and fully empty sensor sections are omitted. There is no
  separate display-layout option or Blueprint preset.
- Installation is uv-managed. The documented launchers are `start_web.bat` on Windows and the
  executable POSIX `start_web.sh` on Linux/macOS. Both run `uv sync --extra web`, create the
  environment, and install Python dependencies plus bundled `ffmpeg` and `ffprobe`. Users do not
  install Python/FFmpeg or edit the system `PATH` separately on supported Windows x64, Linux x64,
  and macOS platforms. Both honor `ROBOCAP_SKIP_SYNC=1` for an already synchronized environment.
- The next distribution target is a ModelScope DatasetHub dataset.
- New dataset uploads use `EgoMotionActions/<YYYYMMDD>/<primitive_id>/<session_id>/`, grouped only
  by the uploader machine's local calendar date. The exact ISO upload start remains in
  `upload_batch_created_at`; retries reuse the assigned date. Legacy `YYYYMMDD_HHMMSS` metadata and
  paths remain readable for compatibility but are never generated by new uploads.
  `EgoMotionActions/Demo/<primitive_id>/<session_id>/` is reserved for migrated legacy examples.
  `P01` through `P29` are built-in action IDs from `EgoMocap Actions.xlsx`, but users may provide
  any safe custom single-directory name. An action ID is not a participant ID.
- A source Session may contain exactly one direct child directory whose name starts with `mocap`,
  matched case-insensitively (for example `mocap/`, `mocap_01/`, or `Mocap-NOKOV/`). Multiple
  `mocap*` source directories are ambiguous and must not be selected silently. ModelScope staging
  always normalizes the published session path to canonical `mocap/`; the source Session is not
  renamed. Legacy `test*` GT discovery remains available for RRD workflows. The top-level local
  collection path may still be named `nokov`; NOKOV remains the vendor/format name.
- On 2026-08-17, the existing `Z:\DATASETS\Frodobots\nokov` collection was migrated in place:
  15 session-level directories, generated analysis/ModelScope path references, three ZIP archives,
  and three RAR archives now use `mocap/`. The collection root itself remains unchanged.
- The complete published dataset hierarchy and required/optional file definitions belong in the
  generated dataset-root `README.md` Dataset Card. The Web UI must not duplicate that structure.
- The published dataset includes the generated inspection HTML for every session. Each report is a
  self-contained HTML file with its JavaScript embedded, is stored with its corresponding session,
  and is referenced by the session manifest.
- ModelScope access tokens or other credentials must never be written to the repository.
- No dataset is uploaded until the target owner/repository, visibility, license or access policy,
  and source-session scope are explicitly confirmed.

## Confirmed ModelScope Layout

```text
<dataset_root>/
  README.md
  metadata.jsonl
  raw_calibration/
    <device_id>/
  EgoMotionActions/
    <YYYYMMDD>/
      <primitive_id>/
        <session_id>/
          <session data files>
          timestamp_anomaly_detail_table.html
    Demo/
      <primitive_id>/
        <session_id>/
          <legacy example files>
```

- Each session remains the primary recording/sample unit and is nested under exactly one action
  primitive directory.
- Participant identity, when available, uses a separate metadata field such as `participant_id` or
  `subject_id`; it must not be inferred from the action primitive ID.
- The dataset-level `metadata.jsonl` has one row per session and includes at least `primitive_id`,
  `session_id`, the packaged data paths, and `inspection_html`.
- The tool prepares direct DatasetHub files under local-only
  `_prepared/<primitive_id>/<session_id>/` rather than publishing only a session ZIP. Upload start
  moves every pending session to the shared local-date directory, updates manifests and metadata,
  and excludes `_prepared/` from transfer. Re-staging updates matching metadata rows without deleting
  unrelated staged files.
- ModelScope authentication uses `MODELSCOPE_API_TOKEN` in the repository-local, Git-ignored `.env`.
  The Web UI can save, clear, and validate it without displaying or logging the saved value.
- The ModelScope dataset repository is stored as `MODELSCOPE_REPO_ID=owner/name` in the same `.env`.
  Web startup restores it, Web save persists it, and CLI `--repo-id` is only a one-command override.
- The active ModelScope dataset repository is `untuitivist/EgoMotionActions`. Its root `README.md`
  is the rendered Dataset Card and must be uploaded whenever the generated dataset documentation changes.
- The generated Dataset Card includes the complete P01-P29 action task catalog, grouped into the six
  collection categories, plus the global operator rules. Every task records its participant instruction,
  geometry, duration, room configuration, and purpose; episodes per participant remain TBD.
- The generated Dataset Card uses ModelScope's native SDK and Git download components instead of a
  detailed `uv` installation guide, and keeps a direct `metadata.jsonl` parsing example.
- Dataset updates are documented by download method: a Git clone uses `git pull --ff-only` (and
  `git lfs pull` if LFS objects remain missing), while an SDK download is refreshed by rerunning the
  SDK download command with the same local directory.
- The active ModelScope repository reports `Apache License 2.0`; the Dataset Card YAML front matter
  must declare the same license.
- The English `Locomotion Primitives` worksheet and the English task records embedded in
  `egomocap-actions.html` were checked field by field and match for all 29 tasks. The workbook's
  `Sheet1` is the corresponding Chinese table.
- Session staging refreshes an existing generated Dataset Card when the template changes, so a staged
  repository cannot silently retain an obsolete action catalog.
- The staged inspection HTML is rewritten through its embedded JSON payload so uploaded reports use
  the session ID instead of a local absolute session path.
- Uploads use the official `modelscope-hub` client and its resumable cache by default.
- One upload publishes every staged session referenced by `metadata.jsonl`; it never publishes a
  complete metadata index while omitting some of the indexed session directories.
- Upload reads the current remote `metadata.jsonl`, merges by `(primitive_id, session_id)` with
  local rows taking precedence, and commits the merged index only after session files succeed.
  This preserves unrelated upload-date groups, legacy timestamp batches, and Demo records without
  requiring their large files
  to exist in the local staging root.
- The Web ModelScope page derives the staging root from the Session directory as its sibling
  `_modelscope_dataset`; users do not enter the same path twice.
- Calibration data is stored once under dataset-level `raw_calibration/<device_id>/`, outside all
  action sessions, and is maintained by a separate calibration workflow. Session staging does not
  copy source-session `raw_calibration/` files. Published session manifests and `metadata.jsonl`
  contain only explicit `device_ids.main`, `device_ids.left`, and `device_ids.right`; an unordered
  related-device list must not infer sides. Local paths, API payloads, and signed URLs are excluded.
- In `EgoMotionActions/<batch>/<primitive_id>/<session_id>/`, the capture streams and
  motion-capture content are required. The concrete NOKOV export formats are optional choices and
  at least one format must be present. Only those format choices and explicitly selected RRD files
  are marked optional.
- ModelScope staging never performs lossy video compression. Full-session video is copied byte-for-byte;
  aligned-intersection crops use lossless encoding and fail if that encoder is unavailable. Legacy CLI
  proxy arguments are accepted for compatibility but cannot enable lossy ModelScope staging.
- ModelScope Web uploads require an existing repository. Repository creation, visibility, and license
  controls remain CLI-only.
- ModelScope Web scans RRD files in the selected Session/Segment and presents them as independent
  checkboxes. Only checked files are staged; an empty selection stages no RRD files. Re-staging
  synchronizes the generated session `rerun/` directory so previously selected files do not remain.
- ModelScope Web also scans every packageable regular file under the Session's unique direct
  `mocap*` directory and presents the files as independent checkboxes. Only BVH, CSV, TRC, and MP4
  are selected by default; a Session-relative path containing `unnamed` is left unselected without
  case sensitivity. Other files remain manually selectable. At least one Mocap file is required.
  Only checked files are staged under canonical `mocap/`, and re-staging removes files excluded by
  the new selection. CLI `--mocap-file` is repeatable; omitting it retains the compatibility behavior
  of including all packageable Mocap files.
- Selecting a Session suggests the ModelScope action primitive from one case-insensitive standalone
  `PXX` token in the direct `mocap*` directory name. The editable dropdown accepts any safe custom
  single-directory name, and explicit user input takes precedence. Missing or conflicting matches
  preserve the current primitive value.
- Web processing starts from a collection root rather than requiring a Session path to be typed for
  every operation. A bounded recursive scan recognizes directories with direct `robocap_*` source
  files, excludes generated/calibration/tooling trees, and exposes relative paths in one searchable
  Session dropdown. The root and last selection persist locally; changing Session clears all file
  controls whose values were derived from the previous Session.
- A Web code-update check is authoritative only after `git fetch --prune origin` succeeds. On fetch
  failure, cached tracking-ref counts may be shown for diagnosis but the remote update status must
  remain unknown. Working-tree dirtiness and remote commit synchronization are separate states.

## ModelScope Publishing Proposal

The following is a proposal based on the ModelScope dataset documentation and is not yet a locked
project definition:

- Keep inspection reports directly accessible as standalone files even when the session data is
  additionally packaged as an archive.
- Add a ModelScope dataset-card `README.md` with YAML `configs`, schema, provenance, alignment
  definitions, known anomalies, license, and loading examples.
- Prefer ModelScope HTTP SDK/CLI upload with resumable cache over manually managing Git LFS for the
  initial large upload.
- Classify the ModelScope Dataset Card under the official `multi-modal` and `cv` domains and the
  `action-recognition` and `body-3d-keypoints` tasks. Keep egocentric video, motion capture, human
  motion, synchronization, and wearable IMU/MAG terms as searchable custom tags.
